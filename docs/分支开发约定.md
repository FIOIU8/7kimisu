# 分支开发约定

这份文档只回答三个问题：**代码放在哪、上游更新怎么接、发版怎么发**。
不涉及内核和管理器的技术细节，那些看 `管理器重写计划.md`。

---

## 一句话版本

`main` 只存"原封不动的上游代码"，你自己所有改动都在 `dev` 分支上。

这样做的唯一目的是：**永远留一份干净的原版**。半年后你改得面目全非时，还能一条命令
`git diff main dev` 看出"我到底动了哪些地方"，也能在上游修复安全问题时快速判断影响范围。

---

## 三个东西分别是什么

| 名字 | 是什么 | 能推吗 |
|---|---|---|
| `origin` | 你自己的 fork：`github.com/FIOIU8/7kimisu` | 能，日常都往这推 |
| `upstream` | 项目原作者仓库：`github.com/hartgerinktarcila-design/7kimisu` | **不能**（推送地址已设为 `DISABLED`，物理上推不上去） |
| `main` 分支 | 上游的镜像，内容永远等于上游最新版 | 只能快进，不接受合并提交 |
| `dev` 分支 | 你自己的开发线，所有改动在这里 | 随便推 |

> 为什么 `main` 要禁掉普通合并？因为一旦 `main` 里混进你自己的提交，它就不再是"原版"了，
> 那份干净的对照物就没了。`--ff-only` 会让这种误操作直接报错而不是悄悄成功。

---

## 场景一：正常改代码（占 95% 的时间）

先确认自己在 `dev` 上，然后正常干活：

```bash
git switch dev          # 不在 dev 就先切过来
# ...改代码...
git add -A
git commit -m "feat: 改了什么"
git push                # 自动推到 origin/dev
```

`push.default` 设成了 `current`，所以 `git push` 不用写分支名，推的就是当前分支。

---

## 场景二：原作者发新版本了

一条命令：

```bash
scripts/sync-upstream.sh
```

它内部做四步：拉上游 → 把 `main` 快进到上游 → 把 `main` 推到你的 fork → 把 `main` 合进 `dev`。

**大概率会冲突**，而且冲突是"整块文件级"的——因为这个仓库的历史被压缩过，每个版本只有
一个提交（就像用快照代替了逐行修改记录），所以上游改动和你改动会以"整个文件不一样"的形式撞在一起。

冲突了就正常解决：打开冲突文件，改到你觉得对的样子，然后

```bash
git add -A && git commit
```

> 提醒：这个仓库的历史是压缩过的，所以 **`git rebase` 完全没有意义**（没有逐行提交可以重放），
> 同步上游只能用 `merge` 或者手工对比。

## 场景三：发版

在 `dev` 上确认编译通过、真机验证过，然后打标签：

```bash
git switch dev
git tag v3.0.0
git push origin v3.0.0
```

标签推上去之后，别忘了 GPL 义务——按 `scripts/pack-source.sh v3.0.0` 打一份对应源码包。
`manager/`、`userspace/` 是 GPL-3.0，`kernel/` 是 GPL-2.0，发 APK 就得能给出源码。

---

## 三件不要做的事

1. **不要在 `main` 上改代码。** 它只负责跟着上游走。真要改，切到 `dev`。
2. **不要 `git push upstream`。** 推不上去（会报错），但更重要的是那不是你的仓库。
3. **不要 `git push --force` 到 `main`。** 那会把你 fork 上唯一的"原版基线"毁掉。

---

## 搞砸了怎么回到已知好状态

```bash
# 我 dev 改乱了，但还没提交 → 全部丢弃，回到 main 那一版
git switch dev && git reset --hard main

# 我 dev 提交了但想撤销最近的提交（保留改动）
git reset --soft HEAD~1

# 我想看看 main 和 dev 到底差了什么
git diff main dev --stat
```

> `reset --hard` 会真的删掉未提交的改动，用之前先确认 `git status` 里没有你想留的东西。

## 构建产物（2026-11-01 已处理）

原先 `manager-next/app/build/` 整个目录（1011 个文件、约 181 MB，含 36 MB 的 `mapping.txt`
和 release APK）被提交进了 git。`.gitignore` 里虽然有 `/target`、`__pycache__` 等规则，
但**完全没有 Android/Gradle 的 `build/` 规则**，所以构建输出一路进了仓库。

后果是：一编译，`git status` 就被上百个中间文件淹没，看不清自己真正改了什么。

已做的处理：

1. `.gitignore` 补上 `build/`、`.gradle/`、`local.properties`、`*.apk`、`*.aab`、`*.jks` 等规则
2. `git rm -r --cached` 把这 1011 个文件移出索引，**磁盘上的文件一个没删**
3. 核对过 `src/main/assets/ksu_manager_gen2`（断代闸门标记）仍正常跟踪——那是源码，
   和 `build/` 里的合并产物是两回事，后者被忽略了不影响编译
4. `.gitattributes` 补充 `*.sh` / `gradlew` 强制 LF（原先只有 `*.bat eol=crlf`）

**遗留**：历史里那 119 MB 还在。要缩只能重写历史（`git filter-repo`），
而重写会与上游彻底分叉、`main` 再也无法 fast-forward，所以不做。
新克隆的仓库仍然要拉 119 MB，这是永久成本。
